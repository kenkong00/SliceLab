## 修复 start.bat 双击启动失败（ABI 不匹配 + 路径空格）

### 根因（有实测证据）
1. **原生模块 ABI 错配**（主因）：`node_modules/better-sqlite3/build/Release/better_sqlite3.node`
   是 ABI **127**（Node 22）编译的，而双击 bat 时 `where node` 解析到系统
   `G:\Program Files\nodejs\node.exe` = **v24.12.0 / ABI 137**。
   后端 `server/db.ts:29` 的 `new Database()` 触发 dlopen → `ERR_DLOPEN_FAILED` → 后端秒崩
   → dev-all 等 `/api/health` 60s 超时 → 整个启动失败。
   - 坑：`require('better-sqlite3')` **不会**暴露这个问题，它只在 `new Database()` 时才 dlopen。
     排查必须直接 `process.dlopen({exports:{}}, <better_sqlite3.node 路径>)` 实测。
2. **spawn 用了 shell:true**（次因）：项目路径含空格 `I:\TREA work\...`，
   走 shell 时整条命令被 cmd 按空格切碎，报 `'I:\TREA' 不是内部或外部命令`。
3. **dev-all 重启计数每次归零**：重启时 new 了新 rec，exitTimes 重置，
   MAX_RESTARTS 永远触发不了 → 后端持续崩溃会每 1.5s 无限重启刷屏。

### 改动
- **新增 `runtime/node/`（98MB）**：固化便携 Node **v22.22.2 / ABI 127** + 自带 npm。
  start.bat 优先用它，从此 ABI 固定，不受系统 Node 版本影响（换电脑直接拷文件夹即可）。
- **新增 `tools/ensure-env.mjs`**：启动前自检 + 自愈
  - 实测 dlopen 检测 ABI 匹配（不是 require）
  - 缺 node_modules / CLI 入口 → 自动 npm install
  - ABI 不匹配 → 先删旧二进制（否则 prebuild-install 会跳过）→ 逐源 rebuild
  - **npm 必须与启动 node 同源**：`process.execPath + npm-cli.js`，
    否则会出现「npm 在 v24 上装了 ABI137，项目用 v22 启动」的错配
  - 下载源：官方 GitHub 超时 90s → 自动切 npmmirror（实测官方卡 5min+，镜像 **6 秒**）
- **`tools/dev-all.mjs`**：`npx tsx/vite` → 直接 `node node_modules/tsx/dist/cli.mjs`、
  `node node_modules/vite/bin/vite.js`（离线可启动，且 taskkill /T 能杀干净）；
  `shell:false`；重启计数继承。
- **`start.bat`** 重写：英文纯 ASCII + **CRLF**（`sed 's/$/\r/'` 转换），不含 `chcp 65001`；
  优先 runtime/node，回退系统 node。

### 验证结果
- `start.bat` 双击链路跑通：5181 `/api/health` → `{"ok":true}`，5180 → HTTP 200
- 破坏性测试：删掉 `better_sqlite3.node` → ensure-env 自动修复成功（63s），dlopen 复验 OK
- `node --check` 两个脚本语法通过

### 换电脑迁移方式
整个 SliceLab 文件夹（含 **runtime/** + node_modules + data）一起拷走即可，零配置双击即跑。
若走 git 且不想带 98MB：把 `runtime/` 加进 .gitignore，新电脑靠 ensure-env 自愈（需联网）。

## 修复「换电脑后图片全部显示不出来」（路径可移植）

### 根因（实测证据）
`images.file_path` / `thumb_path` 存的是**带盘符的绝对路径**：
`F:\TREA work\window操作界面\SliceLab\data\library\sailorMoon1__27.png`
项目在**移动硬盘**上，上一台电脑盘符是 **F:**，这台是 **I:** → `existsSync()` 全 false → 图片读不出来。
（db.ts 原先直接把 `resolve(STORAGE_DIR, ...)` 的绝对路径写进库。）

### 改动（server/db.ts）
- 入库统一存**相对项目根**的路径 `data/library/xxx.png`（`toStoredPath()`）
- 读取按**当前**项目根解析（`resolveStoredPath()`），兼容三种历史数据：
  相对路径 / 当前盘符绝对路径 / 旧盘符绝对路径
- 模块加载时自动跑 `normalizeStoredPaths()`：把残留绝对路径一次性改写为相对路径
  （SQL 只挑 `substr(file_path,2,1)=':'` 的行，不做全表改写）
- 12 处读/写/改名/删除文件的调用点全部改造（grep 复查无遗漏）

### tools/dev-all.mjs 顺带修的坑
- 启动前检测 5180/5181 是否被上次残留占用并自动清理
- **端口占用不能用 `listen()` 判断**：Windows 下 Node 默认带 SO_REUSEADDR，
  端口被占时 listen 照样成功 → 误判为空闲（实测踩到）。改用 `connect()` 探测。
- 沙箱内 Node 的 `execSync("netstat")` 会 EBUSY（仅限本环境，用户双击时正常）

### 验证结果
- 248 行全部转为相对路径，绝对路径行数 **0**，解析后 **248/248** 文件真实存在
- **模拟换电脑**：人为把路径改回 `X:\...` → 启动日志出现
  `[db] 已将 248 条记录的绝对路径改为相对路径`；且不做修复也能直接解析到 I: 盘读到文件
- 图片接口实测：id 27/100/200/248 全部 HTTP 200 + PNG 魔数 `89504e47`
- `tsc -b --noEmit` 通过
- 数据库已备份到 `data/backup-before-pathfix-20261012-041858/`

## 用户反馈「控制台一堆 ERR_CONNECTION_REFUSED」排查结论

**不是路径问题，跟代码无关** —— 上一轮排障收尾时把测试进程全杀了、端口全部清理，
用户浏览器里还开着当时的旧页面，所以刷出：
`Failed to load resource: net::ERR_CONNECTION_REFUSED` + `WebSocket ws://localhost:5180/ failed`
（连接被拒绝 = 没有进程监听，纯"服务没开"）。

诊断要点：**看到 ERR_CONNECTION_REFUSED 先查端口有没有人监听**，别去翻代码。
`netstat -ano | grep -E ":518[01]" | grep -i LISTENING` 为空即服务未运行。

- 切到「素材库」后：**248 个 `<img>`，broken 0**；滚动懒加载 48 → 92 递增
- 截图确认素材库网格全部正常渲染
- API 实测（走 5180 代理，即浏览器真实路径）：`/api/health` 200、

- `vite.config.ts` 里 `/api` → 5181 代理正常，控制台出现 `:5180/api/xxx` 是预期行为

### 已知未修的小限制（非故障）
`id=277` 是 JPEG（文件头 `ffd8ffe0`），缩略图生成器只用 `pngjs`（仅 PNG），
解码失败 → `thumb_path` 为 null → 缩略图接口回退返回原图，**仍能正常显示**，只是没压缩（190KB vs 几十 KB）。
修法需引入纯 JS JPEG 解码器（如 `jpeg-js`，约 50KB），会新增依赖，暂未动。
